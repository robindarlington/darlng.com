`website/public/favicon.svg` — hand-authored, committed, and the single source of truth. It lives in
`public/` because it is itself a served asset, not an input that needs processing; a separate source
copy under `src/assets/` would be a second thing to keep in step. Write exactly this markup, which was
rasterized and visually confirmed during planning to read as a clean geometric `D` at both 32 and 256

  A 64-unit-square `viewBox`, a full-bleed `rect` with a corner radius of 14 filled `#0A0908`, and one
  `path` filled `#2DD9C5` with `fill-rule="evenodd"` whose `d` is
  `M17 13 H31 A19 19 0 0 1 31 51 H17 Z M25 21 V43 H31 A11 11 0 0 0 31 21 Z` — an outer `D` silhouette
  with an inner counter subpath, so the letter reads as a `D` rather than a solid blob.

Set explicit `width` and `height` of 64 alongside the `viewBox` so the raster step has an intrinsic
size to work from. Do not reference a font: Unbounded's geometric character is expressed here in pure
geometry, because an SVG `<text>` element depends on a font being installed wherever the SVG is
rasterized, and the shipped file would render differently on the developer's machine and in the build
container.

`website/scripts/generate-assets.mjs` — add a favicon routine alongside the OG card routine already
proven in `05-01`, sharing the same `sharp` import. Read `public/favicon.svg` once into a buffer, then:

  Produce `public/apple-touch-icon.png` by rasterizing that buffer at a `density` of 384, resizing to
  180x180, and calling `.flatten()` with the `#0A0908` background before writing PNG. The flatten is
  load-bearing, not decorative: iOS applies its own corner mask to a home-screen icon, so the tile's
  rounded corners must be filled to the brand colour rather than left transparent, otherwise the icon
  renders visibly double-rounded with a translucent fringe.

  Produce the 32x32 raster the icon container needs as a buffer using the same density, resized to
  32x32, PNG-encoded, and deliberately NOT flattened — the transparent rounded corners are what make
  the mark sit well on both light and dark browser tab bars.

  Write `public/favicon.ico` by wrapping that 32x32 PNG buffer in a minimal icon container built with
  `Buffer.alloc` and no new dependency. The exact layout, built and confirmed with `file(1)` during
  planning: a 6-byte directory header of three little-endian 16-bit values — 0 reserved, 1 for the icon
  type, 1 for the image count; then a 16-byte entry — an 8-bit width of 32, an 8-bit height of 32, an
  8-bit palette count of 0, an 8-bit reserved 0, a little-endian 16-bit colour-plane count of 1, a
  little-endian 16-bit bit depth of 32, a little-endian 32-bit image byte length at offset 8, and a
  little-endian 32-bit data offset of 22 at offset 12; then the PNG bytes concatenated. An icon
  container has accepted a raw PNG stream as a valid entry since Windows Vista, so no bitmap re-encode
  is needed. Add a head comment recording that `file(1)` is the acceptance gate for this layout.

Keep the routine deterministic and print one line per written icon with its path and the dimensions
read back from sharp, matching the OG routine's self-evidencing log style.

Give crawlers a correct, discoverable map (D-05, D-06).

`website/public/robots.txt` — a static file, four lines exactly, no comments and no trailing content:
a wildcard user-agent line, an allow-all line, one blank line, and a `Sitemap:` directive naming
`https://darlng.com/sitemap-index.xml`. Two things about that directive are deliberate. It is
absolute, because the directive is defined to take a full URL and relative forms are ignored by
crawlers. And it names the index, not `sitemap-0.xml`: the numbered file is the one that looks like
"the sitemap" when browsed, but pointing at it works only while the site fits in a single shard — the
moment a second shard appears, a crawler reading this file would never learn of it (RESEARCH
Pitfall 4). The site must remain fully crawlable: this file grants access, it never withholds it.

Do not add a `filter` option to `astro.config.mjs`. D-06 asks that the error page be absent from the
sitemap, and `@astrojs/sitemap@3.7.3` already drops status-code pages before any user filter runs —
RESEARCH verified this by reading the installed package source, and the sitemap currently emitted by
this repo contains exactly the five real URLs. Assert that outcome rather than adding configuration
that would only restate the default.

`website/nginx.conf` — add one exact-match location so the conventional `/sitemap.xml` path resolves.
The ROADMAP's success criterion names `https://darlng.com/sitemap.xml`, and Astro emits
`sitemap-index.xml`, so without this route that criterion fails at launch and every crawler or human
probing the conventional path gets a 404. Add, after the existing `location /` block and before the
`_astro` block, an exact-match block for `/sitemap.xml` whose only directive is a `try_files` naming
`/sitemap-index.xml` with a `=404` fallback. Serve it rather than redirecting, so the path answers 200
with the index document and the correct XML content type derived from the target's extension.

Declare no `add_header` inside that block. This is the load-bearing detail the file's own head comment
warns about: a location that declares even one `add_header` silently drops every header inherited from
`server{}`, so adding one here would strip the security headers and the cache-control contract from
this response. A block with none inherits all five intact. Change nothing else in the file — the
existing cache-control contract and the repeated header sets in the `_astro` block are verified Phase 1
behaviour.

The HTTP behaviour of this route is asserted against the running container in `05-03` Task 1; this task
asserts the built artefacts and the directive itself.
