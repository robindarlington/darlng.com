Capture screenshots into `/tmp/darlng-phase4/` named `<width>-<state>.png`. The matrix:

At 375 and at 1440, capture all six states — `idle`, `success`, `already-subscribed`,
`error-validation`, `error-network`, `honeypot-success`. At 768, capture `idle`, `success`, and
`error-validation` (the breakpoint that matters at 768 is the input/button row switching from stacked
to inline, which those three exercise). Fifteen files total.

How to reach each state: `idle` is a fresh load scrolled to the section. `success` is a valid, unseen
address submitted once. `already-subscribed` is that same address submitted a second time after a
reload — the mock's synthetic repeat signal. `error-validation` is a malformed address. `error-network`
is a submit with the browser set offline, then set back online. `honeypot-success` is a valid address
with the hidden honeypot field populated via a script-dispatched input event, which must look
identical to `success`.

Beyond the screenshots, assert these four things, each of which is a behaviour the UI-SPEC locks and a
screenshot alone cannot prove:

Pre-hydration posture (UI-SPEC backstop row): load the page and, WITHOUT scrolling, evaluate the
submit button's `disabled` property — it must be true, because `client:visible` has not fired for a
below-the-fold section. Then scroll the section into view, wait for hydration, and evaluate it again —
now false. This is the closest machine-checkable form of the spec's "disabled but not visibly broken"
posture; note in the SUMMARY that the perceptual half stays a human judgement.

Zero CLS: read the privacy note's `offsetTop` before submitting and again after the success state has
rendered. The two values must be identical — the status region's reserved floor is what makes that
true, so a mismatch means the floor is missing or too small. Guard the comparison: if the first read
is not a plain number, fail rather than comparing two empty strings.

Live-region wiring: assert the status region carries `role="status"` and `aria-live="polite"` in the
rendered DOM.

In-flight submit guard (the phase's concurrency contract): with the mock log truncated, submit a valid
address and click the submit button a second time immediately, before the response lands. The log must
end with exactly one line. If a second line appears, the disabled window is too narrow — fix it in the
component.

Kill both background processes when finished, and leave the repository clean: nothing under
`/tmp/darlng-phase4/` is ever committed and every address used is a synthetic `.local` value.
  </action>
