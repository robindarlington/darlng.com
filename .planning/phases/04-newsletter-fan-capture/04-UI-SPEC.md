### New pair: input border (white-alpha, not a `@theme` token)

Per CONTEXT.md's steer ("white/alpha border like Header's `border-white/5`"), verified reasoning below:

| State | Border | Rationale |
|-------|--------|-----------|
| Default | `border border-white/10` | Header's `border-white/5` is a hairline *divider* (sits against the same surface color on both sides, only needs to register as a seam). A form field needs to register as a discrete, tappable *boundary* against the page background — doubling to `white/10` gives it enough definition to read as an input without introducing a new named color token. Still restrained, consistent with the "white-alpha border" family already established. |
| Focus | `1.5px solid var(--color-accent)` + system-wide `:focus-visible` 2px accent outline (offset 2px) | Matches the Secondary/ghost button's 1.5px accent border weight (Phase 2 button contract) — the input "becomes" accent-bordered exactly the way a ghost button does, for consistency. Both the border AND the outline apply simultaneously (belt-and-braces, same pattern already implicit for any bordered interactive element gaining `:focus-visible`). |
| Error | `1.5px solid var(--color-error)` | Same weight as the focus state, swapped to the pre-reserved error token. Overrides the accent focus border while the field is in an error state; a fresh `:focus-visible` still layers the accent outline on top (outline and border-color are independent — no conflict). |

**Placeholder contrast (verified, not eyeballed):** placeholder text uses `--color-text-muted` (`#8C8378`) on the input's `--color-surface` (`#171310`) background — **4.95:1**, already computed and passed in Phase 2's contrast table ("Muted text on surface"). This is placeholder/non-essential text (WCAG does not mandate placeholder contrast at the same bar as content text, but this clears the 4.5:1 AA text floor anyway) — reusing an already-verified pair, no new contrast math required.

### 60/30/10 usage — no changes to the reserved-for list

This phase's accent and error usages both fall inside categories Phase 2 already reserved (CTA fill, form validation). The only genuinely new application is the input surface/border treatment above, which is a *neutral* extension (secondary surface token + a border utility), not a new accent/error category.

## Layout Per Breakpoint

**375px (mobile, default):**
- Heading → pitch line → form, all `flex flex-col`, full content width
- Form: input full-width, `mt-0`; button full-width below it, `mt-2` (8px gap) — **stacked**, not inline
- Both input and button: `min-h-11` (44px), `w-full`
- State message region: directly below the button, `mt-2`
- Privacy note: `mt-3` below the message region

**768px (`md:`) and up:**
- Form becomes a single row: `md:flex md:flex-row md:items-start md:gap-3`
  - Input: `md:flex-1` (grows to fill available space)
  - Button: `md:w-auto md:shrink-0` (intrinsic width, fits its label)
- Max form width: `max-w-lg` (512px)
- State message region: full-width, sits on its own line **below** the input+button row (not inline beside it) at all breakpoints — an inline error next to a `flex-1` input would either truncate or force the row to wrap unpredictably; a dedicated line below is the CLS-safe, wrap-safe choice
- Privacy note: unchanged position, `mt-3` below the message region

**1440px (`xl:`/desktop):** no new behavior — the `max-w-lg` cap means the form doesn't grow further; it simply sits within the already-established 1280px container with the same left-aligned rhythm as the hero and catalog sections above it.

## Form States (exact copy, all four)

The email input and submit button are **never removed from the DOM** across states — only their `disabled`/`aria-invalid` attributes and the button label change, plus the status region's text. This avoids any layout reflow between states (simpler CLS story than swapping the form for a message).

| State | Trigger | Input | Button | Status region text | Status region color |
|-------|---------|-------|--------|----------------------|----------------------|
| **Idle** | Initial render / after hydration | enabled, empty, default border | enabled, label **"Get the drop"** | *(empty — reserved height only)* | n/a |
| **Submitting** (transient) | Valid submit, awaiting fetch response | disabled | disabled, label **"Sending…"** | *(empty — no premature message)* | n/a |
| **Success** | Listmonk returns success | disabled (retains the submitted value, visually muted via native `:disabled` styling) | disabled, label **"You're in ✓"** | **"Check your inbox to confirm."** on line 1, **"We just sent a confirmation link — click it and you're on the list."** on line 2 | `--color-accent` (pre-reserved by Phase 2) |
| **Already-subscribed** | Listmonk response distinguishable as existing subscriber (see caveat below) | disabled | disabled, label **"Already subscribed"** | **"You're already on the list."** | `--color-text` (neutral — not accent, not error; see Color section rationale) |
| **Error — client validation** | Submit attempted with malformed/empty email, before any network call | enabled, `aria-invalid="true"`, `1.5px solid var(--color-error)` border | enabled, label reverts to **"Get the drop"** (never sent) | **"Enter a valid email address."** | `--color-error` |
| **Error — network/API** | fetch fails, non-2xx response, or timeout | enabled (retry) | enabled, label reverts to **"Get the drop"** | **"Something went wrong. Try again in a moment."** — Phase 2's exact, already-locked forward-referenced copy, reused verbatim, not reworded | `--color-error` |

**Already-subscribed distinguishability caveat (documented, not silently assumed):** whether Listmonk's public `/api/public/subscription` endpoint returns a response shape that reliably distinguishes "brand-new subscriber" from "already on this list" is a backend research question CONTEXT.md explicitly defers to planning ("if not distinguishable via the public endpoint, treat as success-equivalent UX and document why"). **This spec locks the already-subscribed copy/visual state regardless of that outcome** — if the endpoint turns out to be indistinguishable, this state is simply unreachable in the shipped build and every successful submission (new or repeat) renders the Success state instead. Both code paths are pre-specified so the planner/executor is never blocked on this research finding either way.

## Honeypot Spec (exact)

```html
<div class="hp-field sr-only" aria-hidden="true">
  <label for="newsletter-hp">Leave this field empty</label>
  <input
    type="text"
    id="newsletter-hp"
    name="hp_website"
    tabindex="-1"
    autocomplete="off"
  />
</div>
```

- **Field name:** `hp_website` — plausible-looking to a naive bot ("website" reads like a real field a scraper might auto-fill), never referenced by real form logic beyond the reject check
- **Hiding technique:** Tailwind's `sr-only` utility (already in use elsewhere in the codebase — `Layout.astro`'s skip link) — clips to a 1px box, not `display:none`. This is a deliberate choice: `display:none`/`visibility:hidden` are the first two things unsophisticated bots check for and skip; the clip-based `sr-only` technique is invisible to sighted users and NOT read by screen readers (because of `aria-hidden="true"` stacked on top — a redundant-but-correct double guarantee, since `sr-only` alone would otherwise still expose it to assistive tech, which the label text "Leave this field empty" is written to be harmless for, but `aria-hidden="true"` fully removes it from the accessibility tree)
- **`tabindex="-1"`:** unreachable via keyboard `Tab` navigation, so a real user can never accidentally focus and fill it
- **`autocomplete="off"`:** prevents browser autofill from populating it for a real user (which would otherwise create false-positive bot detections)
- **Reject behavior:** if `hp_website` has any non-empty value at submit time, the client **silently withholds the real POST to Listmonk** and renders the exact same **Success** state (copy, button label, everything) as a genuine signup. This is the deliberate anti-tell: a bot sees "success" and moves on, gaining no signal that it was caught. No separate visual state exists for this path — it is not one of the "four visible states" because a bot is never shown anything different from a real successful submission.

## Pre-Hydration / No-JS Posture (CLS 0)

**Decision:** the Preact island's markup is present and fully styled from first paint (Astro pre-renders every island's initial output to static HTML regardless of the `client:*` directive — hydration only affects *interactivity*, not markup presence). There is no placeholder/skeleton swap, so there is no CLS risk from the island appearing.

- **Hydration directive:** `client:visible` — the section sits below the fold (after the full hero + 3-card catalog grid), so deferring hydration until scroll-proximity is the correct "lighter option" per CONTEXT.md's explicit steer, and it's very unlikely a fan reaches this section and attempts to type/submit before the browser has hydrated it (hydration completes well before a user scrolls past the catalog grid and reads the pitch line).
- **Pre-hydration button state:** the submit button renders `disabled` in its server-rendered/pre-hydration markup — **same visual treatment as the enabled state** (accent bg, bg text, same padding/radius; no gray-out, no opacity reduction) so it does not "look broken." The only pre-hydration difference is that clicking it does nothing (native `disabled` behavior — no error, no dead click feedback needed since a disabled button gives no click event at all). Once Preact's client-side script mounts, a `useEffect`/mount-time state update flips the button to enabled — this happens automatically as part of `client:visible` hydration, no separate loading indicator needed for this specific transition.
- **Input field:** always focusable and typable, pre- and post-hydration (native `<input>` behavior needs no JS) — a fan can start typing their email while hydration is still catching up, and by the time they reach for the button it will be enabled.
- **`<noscript>` fallback (backstop, cheap to add):** immediately after the form, a `<noscript>` block renders one line of static text: *"This form needs JavaScript. Find DARLNG on Spotify, Instagram, or TikTok below."* — 14px Manrope 400, `--color-text-muted`. This is the honest fallback for the rare fully-JS-disabled visitor; it points at the footer's existing social icon row (already present on every page) rather than inventing a new fallback mechanism.

## Env-Unset Behavior (build-time conditional render)

Per CONTEXT.md: **hide the section entirely** when either `PUBLIC_LISTMONK_URL` or `PUBLIC_LISTMONK_LIST_UUID` is unset at build time — never ship a dead/non-functional form to production.

```astro
---
const listmonkUrl = import.meta.env.PUBLIC_LISTMONK_URL;
const listmonkListUuid = import.meta.env.PUBLIC_LISTMONK_LIST_UUID;
const newsletterEnabled = Boolean(listmonkUrl && listmonkListUuid);
---

{newsletterEnabled && (
  <section id="newsletter" aria-labelledby="newsletter-heading" class="py-12 md:py-16">
    <!-- heading, pitch line, NewsletterForm island, privacy note -->
  </section>
)}
```

Because this is a static (`output: 'static'`) build, when `newsletterEnabled` is `false` the `<NewsletterForm client:visible .../>` invocation never executes during prerendering — Astro only emits an island's hydration script/chunk for pages where the component is actually rendered in the output tree, so the Preact runtime for this island is not shipped at all in an env-unset build. `npm run build` and `npm run check` must both stay green either way (Phase 1's established invariant) — the conditional means an env-unset local/CI build produces a valid page simply missing this one section, not a broken build.
