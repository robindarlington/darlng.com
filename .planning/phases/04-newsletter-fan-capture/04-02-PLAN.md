CORS (RESEARCH Pitfall 4, and the STATE.md decision it corrects) — state the rule first in one line:
configure CORS in exactly ONE place, never two, because a browser rejects a response carrying
duplicate `Access-Control-Allow-Origin` headers outright. Then give the recommended primary: add the
site's origin to Listmonk's own trusted-URLs list, the admin field backing the `security.trusted_urls`
config key (likely under Settings → Security; verify the label against the live UI). Explain in one
line why this is now recommended over the proxy: Listmonk registers its own app-layer CORS middleware
whenever that list is non-empty, so a single admin field replaces hand-written proxy rules and makes a
duplicate-header mistake structurally impossible. Then give the fallback, clearly marked as a fallback
to be used ONLY if the trusted-URLs field turns out not to cover preflight `OPTIONS` on the
subscription route: proxy-level CORS headers at the Traefik/nginx layer in front of Listmonk, with an
explicit instruction to clear the trusted-URLs entry first so only one authority remains. Record that
STATE.md's earlier "CORS at the proxy layer, not the app layer" decision predates the source read that
found the native middleware, and that this section supersedes it.

Bot mitigation — the honest posture (D-10, RESEARCH Pitfall 3). State the finding plainly and without
hedging: Listmonk's ALTCHA and captcha settings guard only its own hosted HTML subscription form
handler; the JSON API route this site posts to has no captcha check at all, so turning captcha on in
Listmonk admin does nothing for this endpoint. Reference that this was read from Listmonk's handler
source and that the upstream request to add captcha coverage for the public API was closed as not
planned. Then list what actually protects the list, in order: the honeypot field shipped in the site's
form, which silently withholds the request client-side and gives the bot no signal (best-effort,
catches naive scrapers only); the fan list's double opt-in, which means an unconfirmed address never
becomes a real subscriber and never receives a campaign; and reverse-proxy rate limiting scoped to the
subscription path, which is the only server-side lever that applies. Give both concrete recipes as
fenced blocks: an nginx `limit_req_zone` keyed on the client address with a matching `limit_req` in a
`location` block for the subscription path, and the equivalent Traefik `rateLimit` middleware label
form applied to the Listmonk service in Coolify. Note which one to use depends on whether Listmonk
sits behind Coolify's bundled Traefik or a separate nginx.

Close the section with a short "What the site does and does not use" list making the API surface
visible and decided: it uses the public subscription POST with `email` and `list_uuids` only; it
deliberately omits the optional `name` field (Listmonk defaults it to the email's local part, and the
form collects email only); it reads but never branches on the response's `has_optin` flag, because
that flag describes the list's opt-in mode and not whether the address was new; it never distinguishes
a repeat subscriber, because the endpoint returns an identical 200 either way, so a fan re-submitting
sees the ordinary success message; and it touches no authenticated Listmonk API, so no Listmonk API
key ever exists in the site build.

Throughout: never transcribe an actual key, selector, record value, or UUID into this file. Where a
value is account-specific, instruct the operator to copy it verbatim from its dashboard, matching
Section 3's existing warning about typing values from memory.
